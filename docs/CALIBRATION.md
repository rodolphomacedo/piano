# Calibration against a reference instrument

How this project intends to find its parameters by **measuring a reference
piano** instead of tuning them by ear. Milestone **M19**, issues
[#123](https://github.com/rodolphomacedo/piano/issues/123)–[#127](https://github.com/rodolphomacedo/piano/issues/127).
Nothing here is implemented yet; this document runs ahead of the code, the
way `docs/PERFORMANCE.md` does.

## Why

Every timbre fix so far (`docs/TIMBRE-PLAN.md`, D1–D12) measured the model
against **theory**: a decay that should be several times faster for H8 than
for H1, a B that should follow Fletcher's curve. That found real defects,
but it cannot answer the reports that are still open:

- [#121](https://github.com/rodolphomacedo/piano/issues/121): the hammer strike is too loud;
- [#122](https://github.com/rodolphomacedo/piano/issues/122): the instrument reads as a guitar.

These are comparisons with a real piano, and theory does not say what a
real A2 decays like at velocity 60 within a factor better than two. A
**target measured with the same code that measures the model** does.

Tuning by ear also does not scale: the model exposes about 40 interacting
sound-shaping parameters, and #80 (re-tune by ear) has stayed open through
every fix.

## The references

| Reference | What it is | How it is driven |
|---|---|---|
| Yamaha P-125 | The owner's digital piano. Sample-based. | The MIDI test set sent into its MIDI input; its audio output recorded |
| GarageBand grand piano | Apple's sampled grand. | The MIDI test set imported and exported to WAV, fully deterministic |
| Others, later | Any instrument that can be driven by a MIDI file | Same protocol |

Both references are **recordings of someone else's recordings**. That is
why this needs an ADR before any code reads a WAV
([#123](https://github.com/rodolphomacedo/piano/issues/123)). The proposed
answer: they are offline measurement targets with the same role
`docs/PRIOR-ART.md` gives OpenPiano. They are a benchmark and never a
source. Their audio never enters this repository or its CI. Only derived
numbers do, with the reference named as their source in
`docs/PHYSICS.md`.

Matching a sampled instrument is a stepping stone, not the goal. The goal
is the method: once it works against a P-125, the same pipeline works
against any instrument whose audio the owner may measure.

## The pipeline

```
MIDI test set (#124) ──┬──▶ model (piano render) ─────────┐
                       ├──▶ GarageBand ──▶ WAV ───────────┼──▶ piano analyze --compare (#125)
                       └──▶ P-125 ──▶ audio capture ──────┘             │
                                                                         ▼
                                       per-key features: decay per partial, B,
                                       attack profile, attack/sustain level, centroid
                                                                         │
                     sensitivity map (#126) ── which parameters ────────▶│
                                                 can move them           ▼
                                       Bayesian estimation (#127, separate repo)
                                                                         │
                                                                         ▼
                                       .piano.json ──▶ studio ──▶ listen
```

### 1. One test set, three instruments (#124)

The same MIDI file, generated by a command, is played through every
instrument. A pianist's hands would make every take different, and the
comparison would then measure the pianist. The first set uses keys A0, C2, A2, C4, A4,
C6, A6 and C8 at velocities 30/60/90/120, each held 8 s, pedal up and down.

### 2. Measure the recording like the model (#125)

`piano-analysis` already computes per-partial decay, the attack's harmonic
profile and the centroid over time, but it places partials using the
model's own B. A recording's B is unknown, so partials are located from
their real FFT peaks and B is fitted. This is the method that found #96.
`--compare` prints model and reference side by side.

### 3. Which parameters can the data see? (#126)

The sound-shaping parameters, grouped by what they plausibly move:

| Group | Parameters | Feature most likely to reveal them |
|---|---|---|
| String losses | `sustain`, `damping`, `loop_zero_mix` | decay time per partial |
| Stiffness | `inharmonicity` | partial frequencies (B) |
| Tuning | `detune_cents` (unison) | beating, two-stage decay |
| Hammer | `mass`, `stiffness`, `contact_exponent`, `felt_bandwidth`, `string_impedance`, `hammer_unevenness` | attack profile, velocity → brightness |
| Excitation | `strike_position`, `excitation_noise_mix` | comb notches in the attack spectrum, noise floor |
| Mechanics | `action_noise_gain`, `damper_strength` | attack-to-sustain level (#121), release |
| Body | `board_load_gain`, `soundboard_mix_gain`, soundboard modes | low-frequency decay, centroid |
| Coupling | `local_coupling_gain`, `global_coupling_gain`, `bridge_coupling` | aftersound, sympathetic ring |
| Extras | `phantom_gain`, `duplex_gain` | non-harmonic partials, treble shimmer |
| Output | `master_gain`, `velocity_curve_exponent`, `limiter_threshold` | absolute level — confounded with each other |
| Room | `room_*` | late tail — capture the references dry and leave these out |

This grouping is a hypothesis. #126 replaces it with a measured parameter ×
feature sensitivity table, and lists the parameter pairs whose effects
cannot be told apart. A parameter the data cannot see has a posterior equal
to its prior, and fitting it only costs sampler time. The first set worth
estimating is probably small: string losses, stiffness, the hammer's
`stiffness` and `felt_bandwidth`, and `action_noise_gain`.

### 4. Estimation (#127)

Lives in a **separate repository** (`piano-calibration-research`, working
name), which depends on this one. Following the Grabatus Bayesian modelling
workflow (Gelman et al. 2020, *Bayesian Workflow*), each stage can fail
cheaply before the next one costs more:

0. **Synthetic recovery.** Render notes from the engine with known
   parameters, measure them, and check that the posterior recovers them
   (posterior recovery and SBC). This needs no recording at all. If the
   model cannot recover its own parameters, it will not recover a Yamaha's.
1. **M1: parameters with a closed form, per key, then hierarchical.**
   B comes from partial frequencies (Fletcher 1964). The loop losses come
   from per-partial decay times (the three-target relation
   `voicing::solve_loop_losses` already uses). A hierarchical model across
   keys yields smooth register curves with uncertainty, replacing the
   hand-drawn anchors of #80.
2. **M2: simulator-only parameters** (hammer, strike position, body). These
   have no closed form. Compare a surrogate (emulator of params → features,
   NUTS on the emulator) against simulation-based inference, with ABC as a
   baseline.
3. **Validation that cannot be gamed.** Fit on some keys and velocities,
   then predict the held-out ones. This is the analogue of rolling-origin
   CV for this problem.
4. **Export** the posterior median as a `.piano.json`, load it in the
   studio, and listen. The ear remains the final test, but it now judges
   a candidate that the measurements have already narrowed down.

## What this does not change

- **No recording ships, ever.** The calibration repository reads audio from
  disk offline. This repository receives numbers.
- None of this runs on the audio thread, and none of
  `docs/REALTIME-AUDIO-RULES.md` applies to it. The estimate becomes
  ordinary parameter values.
- A fitted value still needs a physical reading. A posterior that puts B
  outside Fletcher's published range points to a defect in the model, not
  to a discovery.
